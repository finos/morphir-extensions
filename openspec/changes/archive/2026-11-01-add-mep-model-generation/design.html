Context

See proposal.md for the reason. Both crates implement Extension and Backend of morphir-extension-sdk 0.4.0 and export an Extism guest with export_extension!. The SDK's guest session (ProtocolSession) enforces the lifecycle. For the model draft it also:

  • claims 0.2.0-draft.1 before 0.1 only when ExtensionCapabilities::model_transport holds a tuple that its compiled readers support (model/guest.rs);
  • selects 0.2.0-draft.1 only when the host offers it and sends a model transport offer, intersects complete tuples in the host's order, and takes the lower of each limit;
  • refuses a model method that was not negotiated with CAPABILITY_UNAVAILABLE, and admits every generateModel request before dispatch (validate_model_invocation): agreed tuple, context digest, claimed target and IR version, the envelope's tuple, base64, length, SHA-256, budget and formatVersion, and required guarantees.

The trait default of Backend::generate_model refuses the call, so an extension that advertises a tuple must implement it. The reference is finos/morphir-gleam rust/crates/morphir-gleam-binding/src/model_transport.rs (release extension/gleam/v0.4.0).

Goals and non-goals

Goals: both guests on MEP 0.2.0-draft.1 with generateModel; no change for a host that offers only 0.1; the same artifacts on both lines for the same IR; evidence on the MoonBit worker host.

Non-goals: a change of the Extism ABI (RUN-1 stays); a core-Wasm artifact; an Ion tuple; a model tuple for IR 3; any change of the projections or their options; the finos/morphir bundle pins (a separate pull request).

Decisions

Decided by agents, pending Damian review: MEP-1 to MEP-5, QUA-2 and REL-1. The work order (finos/morphir-extensions#18 and the maintainer's instructions of 2026-11-01) fixes the protocol line, the JSON tuple and the minor releases; the rest follows the Gleam reference.

MEP-1. Both protocol lines through the SDK opt-in

Set model_transport in capabilities() and implement Backend::generate_model. The SDK then claims ["0.2.0-draft.1", "0.1"]. A host that offers only 0.1, or that sends no model transport offer, gets 0.1 and an initialize result without modelTransport, so the Rust host compatibility pins in finos/morphir and older MoonBit CLIs keep working. Alternative: a hand-written dispatcher; rejected, because the SDK session already enforces the draft's negotiation and admission rules.

MEP-2. One JSON tuple for IR 4.0.0, no Ion

morphir.backend.generateModelmorphir-irmorphir-json0.1.0-draft.14.0.0

The SDK has no Ion reader on wasm32 and refuses an Ion tuple from a WASM guest, so the guests cannot offer Ion. The MoonBit CLI offers Ion first and JSON second, and uses the first tuple that the guest agrees on, so it generates with JSON without an error. IR 3 stays on the 0.1 line: model envelopes come from IR v4 frontends, and the Gleam reference offers 4.0.0 only. The limits are those of the Gleam guest (64 MiB encoded, 48 MiB decoded, depth 1024, 16 Mi nodes); the host's lower limits apply.

MEP-3. generateModel reuses generate

generate_model admits the envelope with the SDK's retain_model for the JSON tuple, parses the exact payload bytes as JSON and calls the crate's existing generate_request with that IR, the request's target and its options. The output on the model line is therefore the output of morphir.backend.generate for the same IR, and the existing goldens pin it. Backend-domain failures (an unknown target in OpenAPI, invalid options, IR that does not normalize) stay results with success: false.

MEP-4. Refusals are JSON-RPC errors

An unagreed tuple, an envelope that does not match its tuple, a payload with a wrong length or digest, and a required guarantee are protocol failures. In a session the SDK refuses them before dispatch with INVALID_PARAMS. A direct call of generate_model (no session) refuses them with ExtensionError::InvalidParams. The guests check no guarantee, so they refuse every required one; the Gleam guest answers a failed result in that case, but its session never dispatches such a request either.

MEP-5. One small module per crate

Each crate gets src/model.rs (tuple, support, generate_model, about 60 lines). The two copies differ only in the generate function they call. A shared crate would be a third published crate for one function, and each extension releases on its own.

QUA-2. Both lines in the guest check and in qualify:moonbit

The guest check keeps its 0.1 session (the older-host path) and adds a 0.2.0-draft.1 session on the built module: negotiation with an Ion-first offer, generateModel parity with generate for every IR v4 input, and the refusals. qualify:moonbit writes a JSON envelope for each IR v4 fixture and runs extension generate with it for every target. A run passes when it exits 0 by itself, reports protocol 0.2.0-draft.1 and the JSON tuple, and writes the same files (by SHA-256) as the plain-IR run.

REL-1. Release avro 0.4.0 and openapi 0.5.0

A new protocol line and a new operation are additive: minor versions. The 0.1 output does not change.

Migration plan

No migration: hosts on 0.1 see the same behavior. Hosts that offer 0.2.0-draft.1 can send a model envelope. Rollback is to pin the previous bundles; releases are never replaced.
