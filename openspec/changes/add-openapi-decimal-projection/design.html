Context

See proposal.md for the reason. The projection in rust/crates/morphir-openapi-extension/src/schema/types.rs knows the SDK types Bool, Int, Float, String, Char, Maybe, List, Set, Dict and Result. Any other SDK reference falls through to JSC003 (“no schema projection”). The schema model (src/schema/mod.rs) names no JSON Schema keyword; one shared function, render::schema_body, writes the keywords for both targets, and render/downgrade.rs rewrites the finished 3.1 document to 3.0.

The Avro extension maps Decimal to an Avro bytes decimal with the options decimal_precision (default 38) and decimal_scale (default 10). Avro needs both numbers; JSON Schema does not.

Goals and non-goals

Goals: a Decimal schema that validates the JSON that Morphir data codecs write for a Decimal value, without loss of exactness by default; one projection for both targets; options whose names agree with the Avro extension.

Non-goals: schemas for other SDK types (DEC-6); a value range for the number encoding; checks of the exponent limits of a specific runtime (Elm and MoonBit keep at most 32 fraction digits).

The Morphir IR v4 specification (docs/spec/ir/schemas/v4/index.md) defines only the lexeme of a DecimalLiteral in the IR. It defines no data encoding, no precision and no scale. The OpenAPI format registry has the format decimal (“fixed point decimal of unspecified precision and range”) for both string and number.

Decisions

Decided by agents, pending Damian review (2026-10-31): DEC-1 to DEC-6. The decisions with their evidence went to Damian's main session as a status message. Damian's blanket approval for the Avro and OpenAPI move was extended to this change on the same day.

DEC-1. A pattern-checked string by default

{ "type": "string", "format": "decimal", "pattern": "^-?(0|[1-9][0-9]*)(\\.[0-9]+)?$" }

The pattern accepts every string that a canonical Morphir writer emits ("0", "-0.05", "33500") and the scale-keeping form that some writers keep ("10.50"). It rejects the forms that the Elm decoder silently reads as 0: an exponent, a + sign, ".5", "1.". It also rejects leading zeros, which no writer emits. A JSON pattern is not anchored, so the pattern has ^ and $. The pattern uses only syntax that ECMA-262 and the Rust regex crate read the same way.

Alternatives. The full IR v4 lexeme grammar: wider, but a document valid under it can reach the Elm decoder and become 0. No pattern (morphir-elm's JSON Schema backend): does not check the value at all. A JSON number by default: loses exactness in every binary floating-point consumer.

DEC-2. decimal_encoding for a JSON number

The option decimal_encoding takes "string" (default) or "number". "number" gives {"type": "number", "format": "decimal"}, the shape that the morphir-elm TypeScript backend and morphir-jvm write. The format stays decimal, so a generator can still pick a decimal type. The option name is new: the Avro extension has no equivalent, and representation already means the artifact syntax there.

DEC-3. Optional precision and scale

decimal_precision and decimal_scale mean what they mean in the Avro extension: total significant digits, and digits after the point. Unlike Avro they have no default, because a Morphir Decimal has no fixed precision and JSON Schema needs none. When both are set, the pattern bounds the digits:

CasePattern
p > s > 0 (p = 10, s = 2)^-?(0|[1-9][0-9]{0,7})(\.[0-9]{1,2})?$
s = 0 (p = 5)^-?(0|[1-9][0-9]{0,4})$
p = s (p = s = 3)^-?0(\.[0-9]{1,3})?$

Validation gives JSC002 when only one is set (a scale-only or precision-only rule has no clear Avro counterpart and would need lookahead in the pattern), when the precision is outside 1 to 1000 (the upper limit keeps the repetition count inside what common regex engines compile), when the scale is above the precision, and when either is set with decimal_encoding: "number" (no exact JSON Schema bound exists for binary floating point; multipleOf on a fraction is not exact in most validators).

DEC-4. One schema for both targets and both OpenAPI versions

The projection is target-independent, so the JSON Schema documents and the OpenAPI document get the same Decimal schema. The schema uses only type, format and pattern, which OpenAPI 3.0 has with the same meaning, so the 3.0 downgrade needs no new rule. Maybe Decimal is an anyOf with null in 3.1 and becomes the same keywords with "nullable": true in 3.0, through the existing null-union rule. A test pins this.

DEC-5. Release 0.4.0

The change adds behavior and options and does not change the output for any IR that 0.3.0 accepted, so the version is a minor bump: morphir-openapi 0.4.0. The crate version, claims/expected.json and CHANGELOG.md change in the same pull request. The release follows REL-1 and QUA-1 of the archived change 2026-10-31-move-avro-and-openapi-extensions: the release workflow's dry run from main, then the MoonBit worker host qualification (native and npm entry), then the tag. Before the merge, the PR CI artifact bundles-dry-run is qualified the same way, so a host problem shows before main changes.

DEC-6. Other SDK types in a follow-up issue

The same JSC003 applies to LocalDate, LocalTime, Month, DayOfWeek, Uuid, Instant, DateTime, Regex, Key and the other SDK types that are not in the list in Context. The Morphir tools do not agree on a data encoding for them: morphir-elm DataCodec refuses opaque types such as LocalDate; its JSON Schema backend writes Month as "January" while DataCodec writes custom types as ["january"]; the UUID module has two spellings in morphir-elm. Choosing these encodings is a separate decision per type, so a follow-up issue lists them, with this evidence, instead of this change.

SCH-1. A Decimal variant in the schema model

The model gets Schema::Decimal with the encoding and the optional precision and scale. The renderer turns it into keywords in render::schema_body, so the pattern text exists in one place. The projection reads the options through its existing context.

Alternative. A general pattern and format on Schema::Text: smaller, but it puts JSON Schema keywords into the dialect-neutral model and loses the Morphir meaning.

TST-1. The typed-pricing fixture in every check

apps/morphir-workbench/fixtures/typed-pricing.json from finos/morphir-moonbit (commit fd4026e) is copied, unchanged, into the crate's test fixtures. It is the input of the issue and has both a record and a custom type that use Decimal. It gets golden documents for both targets and both OpenAPI versions, metaschema validation, and instance checks of the Decimal schema. The guest check copies it into its fixture directory (the existing fixture test keeps the two files equal), compares the module with the native crate on it, and adds Decimal option sets; the qualify:moonbit task runs it on the MoonBit host.

Risks and trade-offs

RiskMitigation
A producer that writes the wider IR v4 lexeme (1E+3) fails validation.Documented in the CHANGELOG. Such a string is not safe for the Elm decoder. A consumer that wants a JSON number uses decimal_encoding: "number".
Validators differ in how they treat format: "decimal".In 2020-12 an unknown format is an annotation; the pattern does the checking.
With precision and scale, trailing fraction zeros count toward the scale ("1.500" fails at scale 2).This is also the Avro meaning of scale. Documented in the option description.
The qualification depends on a MoonBit CLI build (npm fix finos/morphir-moonbit#290).Use #290, or main once it merges, and record the commit in the qualification evidence.

Migration plan

No migration: options are additive and the output for IR without Decimal does not change. Rollback is to keep using the 0.3.0 bundle; releases are never replaced.
