Context

See proposal.md for the motivation. The facts below come from finos/morphir-rust 945486e, finos/morphir-moonbit 7dc46bd, finos/morphir 791ce2f and finos/morphir-gleam bc91567 (all main, 2026-10-31).

  • The crates. crates/morphir-avro-extension (version 0.2.0, 14 commits, 86 files) and crates/morphir-openapi-extension (version 0.2.0, 32 commits, 31 files). Both are backends only. Both implement the SDK traits Extension and Backend and export them with export_extension!, so the Wasm module is an Extism plugin: it imports only extism:host/env and exports handle, morphir_extension_info and morphir_extension_capabilities. They claim MEP 0.1 only.
  • Releases. The last releases are extension/avro/v0.2.0 and extension/openapi/v0.2.0 in finos/morphir-rust (commit 04ababf): a .wasm, its .sha256 and a release.json 2.0.0-draft.2 with runtime: "wasm". They have no attestation. Since then only the dependency lines in the two Cargo.toml files changed.
  • Release tooling in finos/morphir-rust. The mise tasks extension:artifact:avro and extension:artifact:openapi run the crate tests, build the module, run the installed-bundle test of morphir-host-native, check Avro IDL with Apache Avro Tools 1.12.2 (Java), and write the bundle with scripts/package_extension.py. That script reads the claims with the extension-claims binary of morphir-host-native. morphir-host and morphir-host-native are not on crates.io.
  • Cross-crate files. One test in each crate reads ../../morphir-projection/tests/fixtures/canonical-customer-v4.json. The Avro README links to two documents in finos/morphir-rust docs/. The extension info of both crates sets the homepage to finos/morphir-rust.
  • The MoonBit worker host (finos/morphir-moonbit #279) runs a WASM guest of either ABI, extism-kernel-v1 or morphir-bytes-v1, from the native CLI and from the Node CLI. It sends plain Morphir IR JSON to morphir.backend.generate on MEP 0.1 (apps/morphir/docs/extension.md). Neither ABI is qualified in a browser yet.
  • finos/morphir pins the two published bundles in .config/published-extension-bundles.toml (a pin without a repository comes from finos/morphir-rust). Its host compatibility CI runs them with the Rust CLI. Its tests generate_extension.rs and generate_openapi_extension.rs build the guests from the ecosystem/morphir-rust submodule.
  • This repository has only the FINOS blueprint. main is not protected and allows merge commits, so the history import can land with a merge commit.

Goals and non-goals

Goals:

  • The two crates, their tests and their history build and test here with no checkout of another repository.
  • A tag gives an attested bundle that a repository index can admit by publisher identity (repository and workflow).
  • The release workflow serves every later extension of this repository, not only these two.

Non-goals:

  • MEP 0.2 generateModel and a core-Wasm (morphir-bytes-v1) artifact. They are a separate later change (RUN-1).
  • Browser support. The bundles do not claim it.
  • Changes to the projection or rendering of either extension.
  • An extension index. The release gives what an index needs; the index is finos/morphir work.

Overview

Solid boxes are in this change. The dashed box is follow-up work in another repository.

Decisions

RUN-1. Keep the Extism guest and MEP 0.1

Decided by agents, pending Damian review (Damian's main session and an independent Codex reviewer, 2026-10-31).

The first releases from this repository ship the same kind of module as before: an Extism guest (extism-kernel-v1) that speaks MEP 0.1.

A. Extism, MEP 0.1 (chosen)B. Core-Wasm, MEP 0.2 (Gleam)C. Both artifacts
MoonBit worker hostRuns (native and Node)RunsRuns
Rust CLI host compatibility in finos/morphirRuns; pins change repository, tag and digest onlyBreaks: the Rust loader needs morphir_extension_infoRuns with the Extism artifact
Work in this changeNone in the cratesByte-channel adapter, generateModel, Wasmtime host testAll of B and two claim sets

Gleam moved to core-Wasm because the MoonBit host then had only the core-wasm-process route. The worker host now runs both ABIs, so that reason does not apply. ABI and MEP version are independent: MEP 0.2 generateModel can come later on the Extism ABI (as in finos/morphir-python), and a core-Wasm artifact only when it gives a demonstrated benefit.

Conditions of the decision: qualify the actual release bundles on the MoonBit worker host, native and Node, in addition to the Rust host compatibility check, before each tag (QUA-1); do not claim browser support.

SET-1. Repository setup

The setup follows finos/morphir-gleam (1ffb06b and later) and finos/morphir-moonbit:

  • OpenSpec. openspec/config.yaml selects the shared html-design schema. openspec/schemas/html-design/, scripts/openspec-ext.mbtx and its feature file are managed snapshots (moonrockz/openspec-ext 0.1.0), locked by openspec/extensions.lock.json. Tasks openspec:check, openspec:validate, openspec:test and openspec:setup. The generated core skills are in each agent directory.
  • mise. .config/mise/config.toml pins node, OpenSpec 1.14.3, bun, actionlint and MoonBit 0.10.18+6c83a7f62 (only for the snapshot checker). With 0.10.18 the managed checker gets the new deprecation warning unfenced_import, and moon test --deny-warn fails on it. The repository-owned task openspec:test therefore disables only that warning (--warn-list -unfenced_import) until upstream moves the imports into frontmatter. The snapshot itself does not change.
  • Agent files. AGENTS.md holds the policy; CLAUDE.md points to it. The pr-monitor skill comes from DamianReeves/skills (locked in skills-lock.json). The build-master skill and agent are in .github/skills/build-master/ and .github/agents/, with discovery links in the agent directories, as in finos/morphir-moonbit; its repository reference describes this repository.
  • Beads. .beads/config.yaml points bd at the shared tracker in finos/morphir (beads-sync), like finos/morphir-python. Work for this repository has the label repo:morphir-extensions.
  • README. The blueprint README is replaced with a description of the repository, its extensions and how to verify a release. The other blueprint files stay.

A rust/ directory leaves room for extensions in other languages and gives CI one path filter. Rust tools are in a separate mise environment, so the OpenSpec job does not install Rust. The crate names stay, so the imported history and the finos/morphir references stay readable.

rust/extensions.toml declares each extension once. The release workflow, the bundle script and the guest check read it, so a new extension needs one entry and no workflow edit.

[extensions.avro]
crate = "morphir-avro-extension"
extension-id = "morphir-avro"
module = "morphir_avro_extension.wasm"
checks = ["rust:avro-idl"]

[extensions.openapi]
crate = "morphir-openapi-extension"
extension-id = "morphir-openapi"
module = "morphir_openapi_extension.wasm"
checks = []

checks names extra mise tasks that the release runs for that extension, so an extension-specific check also needs no workflow edit.

HIS-1. Import the history with git filter-repo

Each crate was created in its present path and never renamed, so the import keeps all commits:

git clone --no-local finos/morphir-rust /tmp/avro-import
git -C /tmp/avro-import filter-repo \
  --path crates/morphir-avro-extension \
  --path-rename crates/morphir-avro-extension/:rust/crates/morphir-avro-extension/ \
  --message-callback '…remove AI co-author trailers, add Imported-from trailer…'
git fetch /tmp/avro-import main:import/avro
git merge --allow-unrelated-histories --no-ff import/avro
# the same for morphir-openapi-extension

EasyCLA checks every commit in a pull request. On 2026-10-31 the 46 commits have no AI co-author trailers. Two commits are from renovate[bot], and one has a Co-authored-by: Damian Reeves trailer. The callback still removes AI trailers, so a commit that lands before the import cannot add one, and adds Imported-from: finos/morphir-rust@<sha> to every commit.

The import pull request is merged with a merge commit, not squashed (Damian's blanket approval covers this). The two imports land in one pull request as two merge commits.

DEP-1. Published Morphir crates only

The crates use morphir-core 0.2.0, morphir-extension-sdk 0.4.0 and morphir-projection 0.1.0 from crates.io (with morphir-json 0.2.0, morphir-workspace 0.2.0 and morphir-config 0.0.1 through them). The check:

  • morphir-extension-sdk, morphir-projection and morphir-json: no commit on finos/morphir-rust main after the commit of their release tag.
  • morphir-core: four commits after 0.2.0 (ff906fe expanded literal members, d04fbe5 and 6cc141c bounded JSON and YAML source decoding, c9be0e7 test only). The extensions use none of these APIs.
  • A scratch workspace with the two crates of 945486e and only crates.io dependencies passes every test target of both crates (15 suites) and builds both modules for wasm32-unknown-unknown.

So no crate release is necessary. If a later change needs an unpublished change, finos/morphir-rust publishes it first by its crate-tag workflow; this repository never adds a git or path dependency.

The shared fixture canonical-customer-v4.json is copied into each crate's tests/fixtures/ from the morphir-projection 0.1.0 source (it has not changed since). The README links into finos/morphir-rust docs/ become absolute links to that repository.

CI-1. One CI workflow with change selection

.github/workflows/ci.yml runs on every pull request and on pushes to main. A changes job reads the changed paths. The openspec and actionlint jobs always run. The rust job (fmt, clippy, tests), the wasm job (build, import check, guest check, bundle script tests, a dry-run bundle of each extension) and the avro-idl job run only when rust/, its mise files, the bundle script or the workflows change. A ci-ok job always runs, needs all others and fails when any of them failed. It is the one check to make required, so a skipped path-filtered job does not block a merge.

Alternative: one workflow per extension with paths filters (finos/morphir-gleam). A skipped workflow cannot be a required check, so that layout has no required check for the extension code.

REL-1. One release workflow for every extension

extension-release.yml runs on tags extension/*/v* and on workflow_dispatch with a tag and a publish flag (default false).

  • check: parse the short id and version from the tag; find the entry in rust/extensions.toml; the version equals the crate version; the tag commit is reachable from main; when publishing, no release exists for the tag. A dry run for a tag that does not exist yet builds the commit it runs on, which must be on main; publishing needs the tag.
  • build (Linux, once): build the module and upload it.
  • test (Linux): crate tests, the guest check on the downloaded module, the claims check and, for Avro, the IDL check. The module is portable Wasm, so one platform is enough; the MoonBit host qualification covers macOS (QUA-1).
  • stage (always): write release.json with the claims that the guest check reads from the downloaded module, write each .sha256, run sha256sum --check, and upload the four files as a workflow artifact. This is the dry-run result.
  • publish (only for a tag push or publish: true; permissions contents: write, id-token: write, attestations: write): download the staged files, check the file set and checksums, run actions/attest@v4 on the module and on release.json, run gh attestation verify --signer-workflow on both, then gh release create "$TAG" --verify-tag --latest=false with the four files.

Other jobs have contents: read only. The bundle script is a bun TypeScript file in .github/scripts/extension-bundle/ with its own tests, as in finos/morphir-gleam.

Later switch to the MoonBit CLI. The bundle and publish steps are to become morphir extension publish --stage and morphir extension publish --release from the MoonBit CLI (finos/morphir-moonbit change acquire-extensions-from-repositories, PR #273, group 3). To make that switch small, the workflow keeps the steps in two named places: one step stages the bundle (release.json, .sha256 files) into a directory, and one job attests and publishes that directory. The switch replaces the stage step with --stage and the gh release create call with --release; the check, build, test, attest and verify steps stay.

QUA-1. Qualify on the MoonBit worker host before a tag

Before each tag, a maintainer runs the dry-run release from main, downloads the bundle and runs the task qualify:moonbit against a MoonBit CLI built from finos/morphir-moonbit main. The task writes a contract 0.2.0 pin that names the module and its release.json, then runs morphir extension describe and morphir extension generate with plain IR JSON for each target, with the native CLI and with the Node CLI. It records the CLI commit, the digests and the command results as JSON. The pull request that prepares the tag holds this evidence and the result of the Rust CLI host compatibility check with the dry-run bundle.

This is a manual gate for now: there is no MoonBit CLI release for Linux to pin in CI (only v0.1.0-demo.1 for macOS arm64). When one exists, the task can run in the release workflow.

Migration plan

  1. PR 1: repository setup and this change (SET-1, CI-1 without the Rust jobs).
  2. PR 2: history import of both crates (merge commit), the rust/ workspace, crates.io dependencies, fixtures and links, the Rust mise environment and the Rust CI jobs. The crates are still 0.2.0.
  3. PR 3: guest check crate, expected claims, Avro IDL task, bundle script, release workflow, homepage and version 0.3.0, README and CHANGELOG.
  4. Dry-run release from main for both extensions; QUA-1 and the Rust host check on the dry-run bundles.
  5. Tags extension/avro/v0.3.0 and extension/openapi/v0.3.0; verify the assets and attestations.
  6. FUP-1 pull requests in finos/morphir and finos/morphir-rust.

Rollback: nothing outside this repository uses the new releases until the finos/morphir pins move. A bad release can be deleted before that; the 0.2.0 releases stay.
